# Technical defense — study guide, not a claim of personal experience

Use this as a guide to study and verify the code yourself. The project was developed with agent assistance; do not claim to have independently designed or implemented a component unless that is true. The current implementation is incomplete. The file paths below are relative to the project root.

1. **Problem.** A user needs to find and inspect evidence in private documents. The application indexes uploaded content, supports multiple retrieval strategies and can ask a configured LLM. Short answer: “It helps search documents and inspect the sources behind an answer.” See `backend/ake_backend/main.py`. Limitation: not all requested features are complete.
2. **Architecture.** React calls FastAPI; PostgreSQL stores metadata, jobs and vectors; a separate worker processes documents. Short answer: “The request layer and long-running indexing are separate.” See `compose.yaml` and `docs/architecture.md`. Follow-up: what happens if a worker dies?
3. **Upload.** The API authenticates the user, checks the knowledge-base owner, validates size and format, stores the file under a generated UUID and creates a persistent job. Short answer: “The upload returns before indexing finishes.” See `main.py`. File and database commits are not one atomic transaction.
4. **Extraction.** PyMuPDF extracts page text; python-docx reads paragraphs and tables; plain files must be UTF-8. Short answer: “PDF page numbers travel with the extracted text.” See `parsers.py`. OCR is not implemented; complex layouts may be incomplete.
5. **Chunking.** A chunk is a bounded slice of normalized text with offsets and overlap. Short answer: “I split text so a model can encode it without silently truncating long documents.” See `text.py` and `worker.py`. Normalized-text offsets are not original-PDF coordinates.
6. **Parameters.** The current embedding path uses 120 model tokens and 16 overlap so chunks fit the selected model's context. Short answer: “These are conservative starting values, not proven optima.” See `worker.py`. Compare alternatives on a larger labelled dataset.
7. **Embeddings.** An embedding maps text to a numeric vector. Similar meanings may be close in vector space. Short answer: “The model turns text into vectors so we can compare meaning.” See `embeddings.py`. Similarity is not proof of relevance.
8. **Embedding model.** The selected multilingual MiniLM model encodes batches on CPU and outputs 384-dimensional normalized vectors; name and revision are stored. Short answer: “The same model and revision must encode documents and queries.” See `embeddings.py`, `config.py`. The model may still miss domain-specific meaning.
9. **Cosine similarity.** It is the dot product divided by the product of vector norms; for unit vectors it is their dot product. Short answer: “It compares direction rather than length.” See the vector SQL in `main.py`. Zero vectors are rejected in `embeddings.py`.
10. **Vector search.** pgvector ranks stored embeddings by cosine distance; an HNSW index is defined in migration 0007. Short answer: “The database retrieves chunks near the query vector.” See `main.py` and `alembic/versions/0007_vector_index.py`. Approximate retrieval and filters can affect recall.
11. **Keyword search.** PostgreSQL full-text search matches lexemes and ranks with `ts_rank_cd`. Short answer: “Keyword search matches words; vector search compares semantic representations.” See `main.py`. `simple` does not provide full Russian or English morphology, and `ts_rank_cd` is not BM25.
12. **Hybrid retrieval.** The application combines ranked keyword and vector lists. Short answer: “The two methods can recover different evidence.” See `main.py` and `retrieval.py`. A fallback searches any term if a plain keyword query gets no hits.
13. **RRF.** Reciprocal rank fusion adds `1/(k + rank)` across lists; this combines positions without assuming scores have the same scale. Short answer: “A chunk ranked well by both lists tends to rise.” See `retrieval.py`. Parameter k and candidate counts affect results.
14. **Reranking.** A reranker scores candidate question–chunk pairs after retrieval. Short answer: “It spends more computation on a smaller candidate set.” See `rerank.py`. If retrieval misses evidence, reranking cannot recover it.
15. **Cross-encoder.** A cross-encoder jointly processes each query and chunk, allowing direct interaction between their tokens. Short answer: “It is usually more expensive than comparing precomputed vectors.” See `rerank.py`. The chosen model is English-oriented.
16. **RAG.** Retrieval-augmented generation supplies retrieved excerpts to a language model before it answers. Short answer: “The answer is conditioned on documents and returns source IDs.” See `rag.py`, `llm.py`, and `main.py`. It does not guarantee truth.
17. **RAG vs fine-tuning.** RAG changes the context at inference; fine-tuning changes model weights. Short answer: “RAG can use newly indexed documents without retraining.” Fine-tuning is not implemented here.
18. **LLM integration.** An adapter sends a chat completion request to an OpenAI-compatible endpoint. Short answer: “The provider is configured separately from retrieval.” See `llm.py`. Real provider generation has not been verified; test doubles are used in automated tests.
19. **Context window.** A model has a finite input/output token budget. Short answer: “We must fit instructions, excerpts and the answer within it.” Current context assembly uses a character cap rather than provider-token accounting; see `rag.py`.
20. **Context limits.** The builder includes only complete excerpts within a fixed character budget. Short answer: “Oversized context is bounded before the provider call.” See `rag.py`. This is approximate and may omit useful evidence.
21. **Hallucinations.** A model predicts plausible continuations and can produce unsupported claims. Short answer: “Grounding reduces risk but cannot make the model infallible.” Source membership checks do not prove entailment.
22. **Citations.** IDs in an answer must be among the supplied chunks, and no-citation answers are rejected. Short answer: “We verify that a cited source was actually provided.” See `rag.py`. This does not check whether the cited sentence supports each claim.
23. **Faithfulness.** Faithfulness asks whether claims follow from the supplied evidence. Short answer: “Valid source IDs alone do not measure faithfulness.” An entailment evaluator and human review are not implemented.
24. **Retrieval evaluation.** Label relevant fragments, run fixed queries and compare metrics under recorded configurations. Short answer: “I would separate retrieval quality from generation quality.” See `evaluation.py` and `docs/evaluation.md`. The current ten-question per-paper seeds use partial anchor labels and are too small for general conclusions.
25. **Recall@K.** The number of relevant items retrieved in the first K divided by the total labelled relevant items. Short answer: “How much of the labelled evidence did we recover?” See `metrics.py`. Incomplete labels distort it.
26. **Precision@K.** Relevant items in the first K divided by K. Short answer: “How much of the result budget is relevant?” See `metrics.py`. This implementation uses K even when fewer results are returned.
27. **MRR.** Mean reciprocal rank averages 1/rank of the first relevant hit across answerable questions. Short answer: “It rewards finding the first useful source early.” See `metrics.py` and `evaluation.py`.
28. **nDCG.** Discounted cumulative gain discounts lower ranks; dividing by an ideal ranking normalizes the result. Short answer: “It measures ranking quality and can use graded relevance.” See `metrics.py`. The current aggregation uses binary labels.
29. **Experiments.** Fix dataset, source version, labels, model revision, chunking, retrieval parameters and environment. Short answer: “Without controlled settings, a difference cannot be attributed to one change.” See `docs/evaluation.md`; the two seed runs changed more than one condition.
30. **PostgreSQL.** A transactional relational database stores users, knowledge bases, jobs, chunks and history. Short answer: “Transactions keep database changes consistent.” See `db.py` and migrations. File-system writes are not transactionally coupled to PostgreSQL.
31. **pgvector.** A PostgreSQL extension stores vector values and provides distance operators and indexes. Short answer: “It lets the same database support metadata and vector search.” See migrations 0002, 0005 and 0007. Filtering approximate search needs recall testing.
32. **asyncio.** Async API/database operations can yield while waiting for I/O; CPU-intensive model calls are dispatched to a thread. Short answer: “Async improves concurrency for waiting, not raw CPU computation.” See `main.py` and `worker.py`.
33. **Worker.** A persistent PostgreSQL job is claimed with a row lock, given a lease and processed outside the HTTP request. Short answer: “An API restart does not erase the queued record.” See `worker.py`. Hard timeouts, cancellation and extensive recovery tests remain.
34. **Testing.** Unit tests cover algorithms and parsing; API tests use SQLite; separate opt-in tests exercise PostgreSQL and pgvector; Playwright covers the browser flow. Short answer: “Mocks test provider contracts, while real models and database have separate smoke checks.” See `backend/tests` and `frontend/e2e`. Coverage is below the requested target.
35. **Security.** Argon2, owner-scoped SQL, validated file keys, bounded uploads and a per-process auth limiter reduce risk. Short answer: “Access checks are independent of the LLM.” See `docs/security.md`. Rate limiting is not distributed; prompt injection is not solved.
36. **Docker.** Compose runs PostgreSQL, migrations, API, worker and frontend with persistent volumes. Short answer: “Each service has a clear local role.” See `compose.yaml`. This is a development configuration, not a hardened production deployment.
37. **CI.** Workflows describe backend checks, PostgreSQL, frontend build, image builds and an E2E run. Short answer: “CI is configured to repeat checks on pushes and pull requests.” See `.github/workflows`. It has not been observed running on GitHub yet.
38. **Limitations.** A large labelled dataset, production security, full streaming, strong grounding verification and complete dashboards remain unfinished. Short answer: “I can describe tested functionality and its limits without claiming production readiness.” See `README.md`.
39. **Scaling.** Separate worker capacity, durable object storage, distributed rate limits, model serving, tenant-aware indexing and monitoring would be candidates. Short answer: “I would measure bottlenecks before choosing infrastructure.” These are future ideas, not implemented features.
40. **Engineering trade-offs.** Current examples include exact source membership versus semantic entailment, safe atomic chunk replacement versus temporary unavailability, and recall versus approximate search. Short answer: “Each decision needs tests and measurements.” Use the code and recorded results to explain what you personally understand; do not claim unverified personal authorship.
